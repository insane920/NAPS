# Замена редактора проводки NAPS: измерения и проверка готового решения

Дата: 31.10.2026. Это техническая проверка пути замены редактора; прототип не включён в обычный интерфейс NAPS и не объявляется завершённой миграцией.

## Проверка предложенной ссылки

Репозиторий [coguy450/fastMEAN](https://github.com/coguy450/fastMEAN) содержит упрощённый стек MongoDB/Express/Angular/Node, а не исходный код электрического редактора FASTMEAN. Его файлы не имеют отношения к проводам. Закрытый код установленной FASTMEAN не извлекался.

Из доступных открытых EDA-редакторов изучен конкретный [планировщик проводов Qucs-S](https://github.com/ra3xdh/qucs_s/blob/current/qucs/wire_planner.cpp): он предлагает прямую, две L-формы и две Z-формы. Это хороший ориентир по предсказуемой геометрии, но весь Qucs-S — Qt-приложение под GPL, а не встраиваемый редактор React. [KiCad](https://github.com/KiCad/kicad-source-mirror) также является отдельным EDA-приложением под GPL.

## Причина лагов в текущем NAPS

При изменении координаты одного узла `SchematicEditor.tsx` перестраивает `routeCircuitWires` для **всех** проводов. Проверка каждого маршрута перебирает чужие сети и тела элементов. Поэтому затраты растут быстрее линейно даже на простой схеме с независимыми прямыми соединениями.

Измерено скриптом `scripts/profile-wiring.ts` на одинаковых тестовых данных, 10 обновлений одной точки после первого расчёта:

| Проводов | NAPS до проверки ограничивающих прямоугольников | NAPS после неё |
| --- | ---: | ---: |
| 50 | около 3 мс | не замерено отдельно |
| 500 | медиана 147 мс | медиана 86 мс |
| 1000 | медиана 603 мс | медиана 332 мс |

В `orthogonalRouter.ts` добавлена предварительная проверка пересечения ограничивающих прямоугольников до точной геометрии. Это сохраняет семантику маршрута, но **не устраняет основной полный пересчёт**. Нынешний установщик от 31.10.2026 был собран до этой экспериментальной оптимизации.

## Выбор готового слоя редактора

Рекомендуемый кандидат — [maxGraph](https://github.com/maxGraph/maxGraph), лицензия [Apache-2.0](https://github.com/maxGraph/maxGraph/blob/main/LICENSE). Он поддерживает [ортогональные стили и обработчик сегментов](https://maxgraph.github.io/maxGraph/docs/usage/cell-handlers/), переподключение концов и [порты компонентов](https://maxgraph.github.io/maxGraph/docs/manual/cells/). Пакет `@maxgraph/core` 0.25.1 добавлен пока только как **devDependency**; он не попал в обычную production-сборку. Опубликованный размер пакета без сжатия — около 7,2 МБ, фактическое изменение EXE после интеграции ещё не измерено.

Изолированный прототип: `maxgraph-wiring-spike.html`, `src/spikes/maxGraphWiring.ts`, `src/spikes/maxGraphCircuitAdapter.ts`; проверка — `scripts/check-maxgraph-spike.cjs`. Для открытия без сервера создан автономный `maxgraph-wiring-demo.html` (сборщик `scripts/build-maxgraph-demo.mjs`). Его прямой запуск через `file://` повторно прошёл ту же браузерную проверку на 100/500/1000 проводах, с импортом контрольной схемы NAPS. В Chrome на простой синтетической схеме:

| Проводов | Создание сцены | Медиана переноса одного узла |
| --- | ---: | ---: |
| 100 | 70 мс | 1 мс |
| 500 | 335 мс | 1 мс |
| 1000 | 1039 мс | 3 мс |

Сравнение с NAPS **не является готовым доказательством ускорения реальных схем**: NAPS здесь измерял построение трасс, maxGraph — перенос уже отображённой простой сцены. Однако разница показывает, что готовый слой может обновлять только затронутый провод. Прототип также проверил: стабильный ID вывода, следование провода за перемещаемым компонентом, сохранение всех элементов, соединений и ручных точек контрольной схемы при импорте/экспорте геометрии. Выбранный ортогональный провод получает встроенный `EdgeSegmentHandler`, то есть обработчик перемещения сегмента доступен без нашего старого кода. Захват элемента за центр с подписью теперь работает в режиме «Выбор»; режим «Проводка» включается отдельно.

После изменения `routeIsClear` прошли `npm run lint`, `npm run test`, `npm run build`, адресный `browser-obstacle-routing.cjs` и полный `npm run test:browser`. Прототип проверен отдельно `node scripts/check-maxgraph-spike.cjs`. Это подтверждает отсутствие обнаруженной регрессии старого редактора; готовый прототип ещё не проходит все проверки SCM 7/8 и не используется в NAPS.

## Что ещё нужно до замены рабочего редактора

1. Перенести SVG-символы и подписи NAPS в графическое представление maxGraph без потери ЕСКД и размеров в миллиметрах.
2. Соединить операции графического редактора с существующими `CircuitElement`/`CircuitWire` и SCM 7/8 одной транзакцией, без второго постоянного источника истины.
3. В режиме SCM 8 нормализовать X/T-пересечения в электрические узлы после пользовательского действия; в SCM 7 сохранять старую топологию. maxGraph сам не знает этих правил.
4. Сохранить ручные изгибы, подключение к конкретному выводу, Undo/Redo, анализы и экспорт. Проверить, что автоматическая перестройка не замыкает разные сети.
5. Сравнить время перетаскивания и построения схем на 10/50/100/500/1000 реальных элементах, а не только на синтетических парах.

31.10.2026: в автономной демоверсии разделены инструменты выбора и проводки. При выборе элемента за центральную подпись он перемещается мышью. Кнопка «Открыть SCM» загружает документ в экспериментальную сцену; повреждённый файл не удаляет открытую схему. Запись обратно в SCM не включена, потому что пока не проверена миграция электрической топологии.

После замечания пользователя воспроизведён конкретный дефект: перемещение середины прямого провода вверх создаёт два ручных изгиба; последующее перемещение B5 оставляло конечный изгиб на старой координате, отчего трасса уходила вправо и возвращалась к B5. `maxGraphBendAnchors.ts` переносит только прилегающую к перемещённому контакту координату ручной точки, сохраняя заданную пользователем высоту участка. Проверка реальной мышью в `check-maxgraph-spike.cjs` подтвердила отсутствие возвратного отростка. Это исправление относится к прототипу; обычный NAPS пока использует прежний редактор.

Проверка воспроизводит порядок действий пользователя «сначала провод, потом B5». После него 25 повторных перемещений B5 туда и обратно вернули в точности прежние ручные точки и видимую трассу. Автономный прототип открыл тестовые SCM 7 и SCM 8; повреждённый файл не заменил открытую схему. `npm run lint`, `npm run test`, `npm run build` и браузерный тест автономного прототипа прошли после исправления.

Экспериментальный адаптер теперь берёт адрес конца провода из фактически подключённого вывода maxGraph. Проверен внутренний цикл SCM 8 «открыть → сериализовать → открыть» для элементов, параметров, проводов, режима пересечений и листа. Отдельная проверка переподключила конец провода к другому выводу и убедилась, что после повторного открытия сохранены новый элемент и номер вывода. Временные JavaScript ID при повторном парсинге меняются — так уже устроен парсер NAPS; сравнение выполнено по порядку элементов, именам и электрическим ссылкам. Кнопки записи файла в прототипе пока нет: для произвольных проектов ещё требуется доказать сохранение топологии и всех поддерживаемых свойств.

Дополнительно проверены удаление существующего и добавление нового провода с последующим открытием SCM. Видимые контакты загруженных элементов имеют 8-пиксельную область захвата при прежней точке электрического подключения; браузерная проверка создала провод мышью между двумя такими выводами. Адаптер отвергает конец, подключённый к неизвестному выводу, вместо молчаливой записи неправильной связи. Электрическая нормализация новых X/T-пересечений и Undo/Redo при открытом SCM пока не проверены; это следующий обязательный этап до кнопки сохранения и встраивания в NAPS.

Добавлен менеджер Undo/Redo. Браузерный тест подтвердил, что после перемещения ручного сегмента и B5 одна команда Undo возвращает одновременно позицию B5 и прилегающую ручную точку, а одна команда Redo восстанавливает обе без отростка. Undo/Redo остальных операций с загруженным SCM пока не проверены. Электрическая нормализация новых X/T-пересечений остаётся главным блокером интеграции.

Изолированно подключён существующий `normalizeCrossingTopology` к фактическим видимым маршрутам maxGraph и затем к `buildCircuitGraph`. На контрольной X-схеме в режиме SCM 8 две изначально раздельные сети после нормализации получили общий электрический узел; при групповом смещении вертикальной ветви сеть разделилась, одна команда Undo восстановила соединение, Redo снова разделила. Та же геометрия в SCM 7 сохранила раздельные сети и не создала автоматических узлов. Эти результаты получены в реальном браузере.

Производные узлы SCM 8 теперь отмечаются на прототипе зелёной точкой. Браузерный тест и визуальный снимок `.work/maxgraph-scm8-crossing.png` подтвердили появление точки на X-пересечении, её исчезновение после разделения сети и восстановление через Undo; для SCM 7 точка не появляется. Маркер пока служит отображением рассчитанного узла и не является самостоятельным перетаскиваемым объектом. Для готовой замены редактора нужно материализовать такой узел в интерактивной модели, проверить T-ответвления и наложения, затем разрешать сохранение SCM.

После последнего изменения повторно прошли `npm run lint`, `npm run build` и автономный браузерный тест `NAPS_SPIKE_FILE=maxgraph-wiring-demo.html node scripts/check-maxgraph-spike.cjs`. Unit-набор `npm run test` проходил ранее в этой итерации; после него изменялись только файлы изолированного прототипа. Windows EXE не собирался.

Ярлык «Руководство FASTMEAN 6.1» указывает на `D:\FASTMEAN 6.1\fastmean_6.0.pdf`. На странице 4 руководство описывает соединение проводом через выводы элементов и отсоединение провода перетаскиванием его конца на свободное место. Это согласуется с отдельными режимами выбора/соединения и проверкой устойчивых привязок. Руководство не описывает семантику электрического X-пересечения; её определяет формат SCM 7/8 NAPS.

До выполнения оставшихся пунктов NAPS использует старый редактор. Прототип остаётся изолированным и не меняет существующие SCM или результаты расчёта.

## Продолжение 01.11.2026: ветвление на существующем проводе

В режиме «Проводка» прототип теперь принимает окончание нового провода на середине существующей трассы. Адаптер создаёт явный `JUNCTION`, разделяет исходный провод на две ветви и присоединяет третью. Узел можно переместить мышью; три видимые ветви остаются у его маркера. Одно Undo удаляет сразу новое ответвление, узел и разделение исходного провода; Redo восстанавливает их. Координата узла и все четыре провода сохраняются при внутренней сериализации SCM 8 и повторном открытии.

Новая браузерная проверка обнаружила повтор имени `N1` при втором ответвлении после сохранения и открытия. Выбор имени исправлен с учётом уже существующих элементов. Проверены два последовательных ответвления, ветвление от трассы с ручными изгибами и сохранение этих изгибов. При присоединении к самому концу провода адаптер теперь повторно использует имеющийся контакт, не создавая нулевой сегмент и наложенный узел.

Браузерная проверка также подтвердила удаление одной T-ветви с Undo/Redo, явное T-соединение в SCM 7 без автоматического объединения остальных пересечений, а также 25 возвратных перемещений узла без накопления изгибов. В этой итерации прошли `npm run lint`, `npm run test`, `npm run build` и автономный браузерный `check-maxgraph-spike.cjs` на 100/500/1000 проводах. После последнего изменения проверки запущены адресно: lint и браузерный тест; `npm run test` и production build ранее прошли в этой же итерации, а последний код затрагивает только изолированный прототип. Для production-сборки потребовалась разрешённая запись временного файла Vite в `D:\FASTMEAN 2.0`; первая попытка без неё завершилась `EPERM`. Тесты проверяют изолированный прототип, не обычное окно NAPS. Действующие EXE не пересобраны.

До встраивания остаются: реальные символы и физический масштаб, проверка удаления и переподключения разветвлённых сетей, полная проверка геометрии после перемещения, сохранение произвольного SCM и сопоставимые измерения на реальных схемах. Кнопка сохранения в прототипе остаётся недоступной.

01.11.2026: производный X-маркер в SCM 8 теперь можно схватить и переместить одним жестом. При нажатии пересечение превращается в один явный `JUNCTION`; оба исходных провода разделяются на четыре ветви. Во время переноса ветви следуют за узлом. Создание и перенос записываются одним действием Undo/Redo; Esc отменяет весь жест. После повторного открытия SCM 8 остаются четыре ветви и новые координаты узла. Проверка показывает, что SCM 7 не получает автоматического X-узла. Положение маркера обновляется при изменении масштаба. Это изменение всё ещё относится к автономному прототипу, не к обычному редактору NAPS.

Дополнительная проверка выявила, что вновь созданная T-ветвь имела прямой стиль maxGraph до сохранения и ортогональный после открытия SCM. Это меняло видимую трассу, хотя связь сохранялась. При создании T-ветви теперь сразу задаётся ортогональный стиль. Браузерный тест сравнивает все видимые точки ветвей до и после открытия, проверяет ортогональность после переноса узла и проходит. Во время перетаскивания X-узла отложен дорогой пересчёт производных маркеров до отпускания мыши.

Остаётся выполнить реальную миграцию основного интерфейса: перенести символы и размеры, сопоставить состояние maxGraph с React и приложением, проверить свойства, расчёты, печать и файлы на пользовательских схемах. До этого нельзя назвать замену проводки завершённой или пересобирать EXE как исправленную версию.

## Подключение к основному окну 01.11.2026

В `App.tsx` добавлена команда «Новая проводка». Она открывает встроенное окно maxGraph с текущим документом; закрытие без применения не меняет проект. Перед применением окно возвращает SCM и геометрию, основной процесс повторно разбирает SCM, нормализует пересечения SCM 8 и проверяет геометрию. Только после этих проверок изменения элементов и проводов вносятся одной группой истории NAPS. Если основной проект изменился после открытия окна, применение отвергается. Production-сборка теперь включает отдельную страницу редактора; начальный основной JS не содержит maxGraph.

Браузерный тест реального интерфейса подтвердил: перенос элемента в новом окне → применение → сохранение SCM → координата сохраняется; один Undo восстанавливает исходную координату, Redo повторяет перенос; закрытие окна без применения ничего не меняет. Второй сценарий мышью создал T-ветвь в новом окне; после применения и сохранения SCM остались один явный узел, три провода и электрическое соединение с нужным выводом. `npm run lint`, `npm run test`, `npm run build` и весь `npm run test:browser` прошли. Сборка Vite добавляет отдельный модуль проводки около 452 КБ (121 КБ gzip); размер EXE не измерялся, EXE не пересобирался.

Это доступный пользователю путь к новой проводке, но **не полная замена** старого SVG-редактора. Встроенное окно пока показывает упрощённые прямоугольные символы и не содержит всех панелей свойств, размещения и печати. Основной холст использует прежнюю реализацию. Нужны общие компоненты отображения, настройка физического масштаба, прямое редактирование без отдельного окна и полная проверка загрузки/сохранения пользовательских схем перед отказом от старого холста.
